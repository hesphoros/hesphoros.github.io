# Unicode 编码
  世界上存在着多种编码方式，同一个二进制数字可以被解释成不同的符号。因此，要想打开一个文本文件，就必须知道它的编码方式，否则用错误的编码方式解读，就会出现乱码。
  
  > 为什么电子邮件常常出现乱码？
  > ANS: 就是因为发信人和收信人使用的编码方式不一样。

可以想象，如果有一种编码，将世界上所有的符号都纳入其中。每一个符号都给予一个独一无二的编码，那么乱码问题就会消失。这就是 Unicode，就像它的名字都表示的，这是一种所有符号的编码。

Unicode 当然是一个很大的集合，现在的规模可以容纳100多万个符号。每个符号的编码都不一样，比如，`U+0639`表示阿拉伯字母`Ain`，`U+0041`表示英语的大写字母`A`，`U+4E25`表示汉字`严`。具体的符号对应表，可以查询[unicode.org](http://www.unicode.org/)，或者专门的[汉字对应表](http://www.chi2ko.com/tool/CJK.htm)。

# Unicode’ problem
**Unicode 编码的典型问题：**

- 多种编码方式导致兼容性难题
- 标准不断扩展带来的兼容与支持问题
- 复合字符与规范化带来的比较、搜索、排序困扰
- 字符宽度、显示和长度处理复杂
- 文本处理算法难度增加
- BOM 引发的读取问题
- 不同库和系统支持不一致，带来安全风险



## 1. 多种编码方式导致兼容性问题

- **UTF-8、UTF-16、UTF-32** 等不同编码方式同时存在，同一个 Unicode 字符在不同编码下占用的字节数不同，造成跨平台或跨系统数据交换时容易出错。
- 文件或网络传输时，如果未明确标注编码方式，容易出现乱码或解析失败。

## 2. 字符集扩展及历史包袱

- Unicode 标准不断扩展，增加了许多新的字符（如 emoji、古文字），老旧系统或库可能无法支持最新字符，导致显示或处理出错。
- 与早期编码（如 GBK、Big5、ISO-8859-1）兼容时，需要复杂的转换过程，容易出错或丢失信息。

## 3. 复合字符与规范化问题

- 某些字符有多种表示方法（如“é”可编码为 U+00E9 或 U+0065+U+0301），不同系统或库处理规范化的方式可能不同，导致文本比较、搜索、排序出现不一致。
- 正规化（Normalization）没做好时，可能导致安全漏洞（比如 IDN 同形攻击）。

## 4. 字符宽度与显示问题

- 某些字符（如 CJK 全角字符、emoji）宽度不同，多字节字符会影响 UI 排版、终端显示、字符串截断等，尤其在“字符数”和“字节数”不等价时容易出错。
- 计数“字符长度”时容易混淆（如 Python 的 `len()` 在不同编码下结果不同）。

## 5. 文本处理复杂度提升

- 字符串切割、反转、查找等操作不再是简单的字节操作，需要考虑多字节、复合字符和变长编码。
- 某些算法（如正则表达式）在 Unicode 下需要特别处理，才能正确支持全部字符集。

## 6. “BOM”问题

- UTF-8、UTF-16 等编码在部分平台会加上 BOM（字节顺序标记），而有些程序不支持 BOM，导致读取文件时出错或多出不可见字符。

## 7. 兼容性与安全性

- 不同语言、库对 Unicode 支持程度不一，尤其是早期库或跨语言数据交换时，容易出现漏洞或安全隐患（如 XSS、SQL注入中利用 Unicode 绕过过滤）。

1. **如何区分不同编码长度的符号（变长/定长）？**
2. **如何避免英文字母等常用字符的存储空间浪费？**

这两个问题直接导致了**Unicode有多种存储方式（编码实现）**的出现，也影响了 Unicode 在实际中的普及速度。

### Unicode 的存储和编码方式问题

Unicode 只是一个符号集，它规定了每个字符对应的唯一“码点”，比如汉字“严”的 Unicode 码点是 0x4E25。但 Unicode 标准本身**不规定码点的实际存储方式**。在实际存储和传输时，面临两个主要问题：

---

#### 1. 变长与定长编码的区分问题

- **问题描述**：比如“严”的码点是 0x4E25（15 位二进制），但计算机处理数据一般以字节为单位。如果简单地把每个字符都用固定的字节数（比如 2、3 或 4 字节）存储，会造成空间浪费；如果用变长字节存储，就需要一种机制区分字节序列是一个字符还是多个字符。
- **影响**：如果没有统一的分隔和标记方式，计算机无法区分哪些字节是一个字符，哪些是多个字符的组合，也无法与早期的 ASCII 编码兼容。

#### 2. 空间浪费问题

- **问题描述**：早期 Unicode 的 UCS-2/UCS-4 等定长编码，每个字符固定用 2 或 4 字节。如果用 4 字节存储英文字符（实际只需 1 字节），就会造成大量冗余和空间浪费，尤其是在以英文为主的文本中。
- **影响**：文本文件体积暴涨两三倍，存储和传输成本大幅增加，企业和用户难以接受。

---

### 解决方案：多种 Unicode 存储方式（编码）

为了解决上述问题，Unicode 制定了多种实际存储方式，最常见的有：

- **UTF-8**：变长编码，每个字符 1~4 字节，兼容 ASCII，英文字符仍用 1 字节，汉字等用 3 字节。
- **UTF-16**：变长编码，每个字符 2 或 4 字节，常用于 Windows/Java。
- **UTF-32（UCS-4）**：定长编码，每个字符 4 字节，编码和解码简单，但空间消耗大。

---

### Unicode 普及的历史阻力

- 由于兼容性、存储效率和实际应用的复杂性，Unicode 在互联网普及前很长一段时间难以推广。
- 直到互联网和全球化需求爆发，跨语言文本处理变得越来越重要，UTF-8 这种兼容、灵活、高效的编码方式才成为事实上的主流标准，加速了 Unicode 的普及。

---

## 总结

- Unicode 是字符集和符号集，不规定实际存储方式。
- 存储时面临字符长度区分和空间浪费两大难题。
- 解决方式是发展出多种实际编码（UTF-8、UTF-16、UTF-32等）。
- 这些问题也影响了 Unicode 的历史推广进程。
