# Issue #5 技术细节：C++14 无注册聚合反射

本文是 [Boost.PFR Issue #5](https://github.com/boostorg/pfr/issues/5) 的代码级学习笔记，重点解释其中 `as_tuple` 原型为什么能够在 C++14 中推导聚合体的字段数量和字段类型，以及这个方案为什么不能简单地视为“安全的 `struct -> std::tuple` 转换”。

> 阅读前提：熟悉模板参数包、SFINAE、`decltype`、`std::index_sequence`、聚合初始化和引用折叠。

## 1. 目标与边界

目标类型是可以进行聚合初始化的用户类型，例如：

```cpp
enum class color { red, green, blue };

struct reg {
    int a;
    char b;
    double d;
    void* e;
    color f;
    std::string g;
};
```

期望得到一个无注册入口：

```cpp
reg value{42, 'a', 3.1, nullptr, color::green, "hello world!"};

as_tuple(value, [](auto&& tuple_view) {
    // 可以使用 std::get<0>(tuple_view) 等 tuple 操作
});
```

它不试图完成以下事情：

- 推导成员名称；
- 处理任意非聚合类；
- 修改类的私有成员；
- 在标准层面保证任意类型都能安全地转换成 `std::tuple`；
- 在 C++14 中提供与 C++17 结构化绑定完全相同的 `constexpr` 语义。

因此，这是一种**面向聚合体的编译期类型探测 + 运行时字段访问**技术。

## 2. 总体数据流

```text
T
│
├─ 生成 T{ubiq<0>{}, ubiq<1>{}, ...}
│       └─ SFINAE 判断聚合初始化是否成立
│
├─ 得到字段数量 N
│
├─ 生成 T{Props{}..., deduce(callback)}
│       └─ deducer<T>::operator T() 被隐式调用
│          callback(type<T>{}) 记录当前字段类型
│
├─ 得到 Props... = P0, P1, ..., P(N-1)
│
└─ 将 object 交给 reinterpret_cast<std::tuple<Props...>&>
        └─ visitor 使用 std::get<I>
```

这里有两个不同的“探测”：

1. **数量探测**：只关心 `T{...}` 是否有效；
2. **类型探测**：利用隐式转换目标类型，捕获每个字段的类型。

将二者分开理解，是读懂这段模板代码的关键。

## 3. 类型标签：只传递类型，不创建对象

原型中使用了一个空标签类型：

```cpp
template <typename>
struct type {};
```

`type<T>` 的作用类似标准库中的 `std::type_identity<T>`：它携带 `T` 这个类型，但本身不保存任何值。

例如：

```cpp
template <typename T>
void inspect(type<T>);
```

调用 `inspect(type<int>{})` 时，函数可以在模板参数层面知道 `T == int`，但不会构造一个 `int`。

原型通过它把“当前字段类型”传回回调：

```cpp
callback(type<field_type>{});
```

## 4. 用 `ubiq` 检测字段数量

### 4.1 万能转换占位符

```cpp
template <std::size_t I>
struct ubiq {
    template <typename T>
    operator T() const;
};
```

`ubiq<I>` 声明了一个转换函数模板，因此在表达式中，它可以被当作任意字段类型的初始化实参：

```cpp
reg{
    ubiq<0>{},
    ubiq<1>{},
    ubiq<2>{}
};
```

对于 `reg`，这相当于尝试把三个占位对象分别转换成 `int`、`char` 和 `double`。如果再添加第四个参数，也就是把 `ubiq<3>` 转换成 `void*`，初始化仍然有效。

### 4.2 用 `void_t` 把表达式变成 SFINAE 条件

```cpp
template <typename...>
using void_t = void;
```

下面的偏特化只有在 `T{ubiq<head>{}, ubiq<tail>{}...}` 合法时才参与匹配：

```cpp
template <typename, typename, typename = void>
struct size_impl;

template <typename T, std::size_t Head, std::size_t... Tail>
struct size_impl<
    T,
    std::index_sequence<Head, Tail...>,
    void_t<decltype(T{ubiq<Head>{}, ubiq<Tail>{}...})>
> : std::integral_constant<
        std::size_t,
        sizeof...(Tail) + 1
    > {};
```

这里的表达式只用于 `decltype`，不会在运行时执行。但是编译器必须检查它是否满足聚合初始化规则，因此可以借此进行编译期判断。

如果初始化不合法，则上面的偏特化失效，SFINAE 会选择递归版本：

```cpp
template <typename T, std::size_t Head, std::size_t... Tail, typename Failure>
struct size_impl<
    T,
    std::index_sequence<Head, Tail...>,
    Failure
> : size_impl<T, std::index_sequence<Tail...>> {};
```

递归过程可以理解为：

```text
尝试 N 个占位参数
  ├─ 成功：字段数量 = N
  └─ 失败：尝试 N - 1 个参数
```

最终入口是：

```cpp
template <typename T>
struct size : size_impl<
    T,
    std::make_index_sequence<sizeof(T)>
> {};
```

### 4.3 为什么用 `sizeof(T)` 作为上界

这个上界不是字段数量，而只是一个足够大的探测范围。对于常见的聚合体，字段数量通常远小于对象大小，因此 `sizeof(T)` 能提供一个简单的上界。

例如：

```cpp
struct S {
    int x;
    double y;
};
```

在多数 ABI 上 `sizeof(S) >= 2`，探测会从较大的参数个数递减到 `2`，然后发现 `S{ubiq<0>{}, ubiq<1>{}}` 有效，而添加第三个初始化器无效。

这个做法的代价是模板实例化次数可能较多，而且它依赖“对象大小足以覆盖字段数量”这一经验性上界。后来的实现会对字段计数机制进行更严谨的封装。

## 5. 用 `deducer` 捕获字段类型

字段数量只能告诉我们需要多少次访问；要构造 `tuple<Props...>`，还必须知道每个字段的类型。

### 5.1 `deducer` 的转换运算符

```cpp
template <typename F>
struct deducer {
    F f;

    template <typename T>
    operator T() const {
        f(type<T>{});
        return {};
    }
};
```

假设 `deducer` 被用作一个聚合初始化实参：

```cpp
reg{deducer{callback}}
```

编译器需要把这个对象转换成 `reg` 当前字段所要求的类型。例如第一个字段是 `int`，就会实例化：

```cpp
deducer<Callback>::operator int()
```

于是模板参数 `T` 就等于 `int`，回调收到：

```cpp
callback(type<int>{});
```

如果下一个字段是 `char`，同一个转换模板会被实例化为 `operator char()`。这就是“通过隐式转换目标捕获字段类型”。

### 5.2 `deduce` 只负责保存回调

```cpp
template <typename F>
deducer<std::decay_t<F>> deduce(F&& f) {
    return {std::forward<F>(f)};
}
```

`deduce` 的作用有两个：

1. 去除回调的引用属性，得到可存储的闭包类型；
2. 返回一个具有万能转换运算符的对象。

它本身不推导字段；字段推导发生在这个对象被放进 `T{...}` 之后。

## 6. 为什么字段类型会按顺序被捕获

关键表达式是：

```cpp
std::decay_t<T>{
    Props{}...,
    deduce([&](auto prop) {
        as_tuple_impl(
            f,
            t,
            type<Props>{}...,
            prop
        );
    })
};
```

假设已经捕获了 `P0, P1`，那么当前表达式近似为：

```cpp
reg{
    P0{},
    P1{},
    deduce(callback)
};
```

聚合初始化会把前两个初始化器交给前两个字段，最后一个 `deduce(callback)` 必须转换成第三个字段的类型 `P2`。转换发生时，回调获得 `type<P2>{}`，然后递归调用：

```cpp
as_tuple_impl(
    f,
    t,
    type<P0>{},
    type<P1>{},
    type<P2>{}
);
```

下一轮会继续尝试第四个字段。于是参数包逐步增长：

```text
as_tuple_impl(f, t)
as_tuple_impl(f, t, type<P0>{})
as_tuple_impl(f, t, type<P0>{}, type<P1>{})
as_tuple_impl(f, t, type<P0>{}, type<P1>{}, type<P2>{})
...
```

这是一种**递归参数包累积器**：参数包中的类型既是已经发现的字段列表，也是下一次聚合初始化时需要跳过的字段类型列表。

## 7. `as_tuple_impl` 的两个终止条件

### 7.1 尚未发现全部字段

```cpp
template <typename F, typename T, typename... Props>
auto as_tuple_impl(F&& f, T&& t, type<Props>...)
    -> std::enable_if_t<
        size<std::decay_t<T>>::value != sizeof...(Props)
    >;
```

当 `sizeof...(Props)` 小于真实字段数量时，函数进入探测分支：

1. 用 `Props{}...` 填充已经发现的字段；
2. 用 `deduce(callback)` 作为下一个字段的初始化器；
3. 从隐式转换目标类型中得到下一个字段类型；
4. 递归调用自身。

`std::enable_if_t` 只保留返回类型，不返回实际值；这个函数的效果发生在模板实例化和回调调用过程中。

### 7.2 已发现全部字段

```cpp
template <typename F, typename T, typename... Props>
auto as_tuple_impl(F&& f, T&& t, type<Props>...)
    -> std::enable_if_t<
        size<std::decay_t<T>>::value == sizeof...(Props)
    >
{
    std::forward<F>(f)(
        reinterpret_cast<std::tuple<Props...>&&>(t)
    );
}
```

当字段数量和参数包长度相等时，递归结束，所有字段类型已经被收集。此时才调用用户 visitor。

注意这里把 `t` 转成了右值 tuple 引用，因此它还试图保留传入对象的值类别。

## 8. 左值与右值重载为什么要分开

原型另外提供了一个左值版本：

```cpp
template <typename F, typename T, typename... Props>
auto as_tuple_impl(F&& f, T& t, type<Props>...)
    -> std::enable_if_t<
        size<T>::value == sizeof...(Props)
    >
{
    std::forward<F>(f)(
        reinterpret_cast<std::tuple<Props...>&>(t)
    );
}
```

两个版本的区别是：

| 输入对象 | tuple 视图 | visitor 能否修改原对象 |
| :--- | :--- | :--- |
| `T&` | `std::tuple<Props...>&` | 可以 |
| `T&&` | `std::tuple<Props...>&&` | 取决于字段引用和值类别 |

如果所有入口都把对象转换为右值，左值对象也会丢失可修改的引用语义。单独的 `T&` 重载可以避免这一点。

`std::decay_t<T>` 只用于数量检测，是为了去除 `T&`、`T&&` 和 `const` 等传递形式差异；左值访问路径则保留原始 `T`。

## 9. `as_tuple` 只是把内部实现包装起来

最终入口很小：

```cpp
template <typename T, typename F>
auto as_tuple(T&& t, F&& f) {
    as_tuple_impl(
        std::forward<F>(f),
        std::forward<T>(t)
    );
}
```

它把两个用户参数完美转发到递归实现：

- `T` 决定对象类型和值类别；
- `F` 决定 visitor 类型和值类别；
- `Props...` 由后续模板实例化自动生成。

## 10. 用 `reg` 跟踪一次完整实例化

对于：

```cpp
reg value{42, 'a', 3.1, nullptr, color::green, "hello world!"};

as_tuple(value, visitor);
```

可以把实例化过程简化成下面的表：

| 阶段 | 当前参数包 | 触发的初始化 | 新发现的类型 |
| :--- | :--- | :--- | :--- |
| 0 | 空 | `reg{deduce(visitor)}` | `int` |
| 1 | `int` | `reg{int{}, deduce(visitor)}` | `char` |
| 2 | `int, char` | `reg{int{}, char{}, deduce(visitor)}` | `double` |
| 3 | `int, char, double` | `reg{..., double{}, deduce(visitor)}` | `void*` |
| 4 | `int, char, double, void*` | `reg{..., void*{}, deduce(visitor)}` | `color` |
| 5 | `int, char, double, void*, color` | `reg{..., color{}, deduce(visitor)}` | `std::string` |
| 6 | `int, char, double, void*, color, std::string` | 数量相等，结束递归 | 调用 visitor |

于是最终类型列表为：

```cpp
std::tuple<int, char, double, void*, color, std::string>
```

需要强调：这个 tuple 类型是元编程阶段构造出来的**类型描述**；原始原型并没有真正创建一个独立的 `std::tuple` 对象，而是尝试把原对象的地址解释成该 tuple 类型的引用。

## 11. 最危险的一步：`reinterpret_cast`

原型最后依赖：

```cpp
reinterpret_cast<std::tuple<Props...>&>(object)
```

这隐含了几个非常强的假设：

1. `std::tuple<Props...>` 的内存布局与用户类型完全匹配；
2. tuple 的每个元素和用户类型的每个字段处于兼容位置；
3. 通过 tuple 类型访问不会违反对象生命周期规则；
4. 不会违反严格别名和类型访问规则；
5. 对不同标准库实现都成立。

这些假设不是 C++ 标准对任意 `struct` 和 `std::tuple` 的保证。Issue 原文也明确注明，原型只在 Clang + libc++ 环境下工作，因为它依赖这种实现层面的布局行为。

### 11.1 为什么优化器生成零开销仍然不够

Clang 可能在优化后把 tuple 视图完全消除，最终只保留对原字段的直接访问。但优化发生在语义检查之后：

```text
先判断程序是否合法
再进行优化
```

因此，优化器能消除中间对象，并不意味着原始 `reinterpret_cast` 自动变成了标准允许的对象访问。

### 11.2 为什么 union 方案也不简单

讨论中曾尝试使用：

```cpp
union {
    some_type source;
    tuple<Props...> view;
} u{source_object};
```

希望利用 standard-layout union 的 common initial sequence 规则。但这需要参与访问的类型满足严格条件，而 PFR 使用的内部 tuple 类型未必是 standard-layout；此外，union 初始化可能导致一次复制，也不适合需要保留原对象引用的场景。

所以，union 方案不能作为普遍的安全修复。

## 12. 构造副作用：探测表达式并不一定“无成本”

虽然字段计数表达式出现在 `decltype` 中，但类型捕获阶段包含真正的表达式：

```cpp
return {};
```

以及：

```cpp
std::decay_t<T>{
    Props{}...,
    deduce(callback)
};
```

如果 `T` 或字段类型包含用户定义构造函数，编译器可能在求值上下文中执行多次构造和析构。Issue 讨论中，一个五元素测试对象被观察到发生大量默认构造，维护者因此要求限制启用条件。

典型风险类型包括：

```cpp
struct noisy {
    noisy() { log("construct"); }
    ~noisy() { log("destroy"); }
};

struct aggregate {
    noisy value;
};
```

对这种类型进行“字段推导”可能触发日志、锁、内存分配或其他副作用。反射库不能假设“只是探测类型”就一定不会运行用户构造代码。

后续工程化实现倾向于要求类型满足更严格的条件，例如能够进行 `constexpr` 聚合初始化，从而让编译器可以确认构造过程可计算且没有不可接受的副作用。

## 13. 为什么 `constexpr` 是语义问题

结构化绑定属于语言语法，可以直接参与某些常量表达式路径；而这个原型的 tuple 视图是在回调调用点通过 `reinterpret_cast` 形成的。

即使编译器能把下面的运行时代码优化得很好：

```cpp
as_tuple(reg{...}, [](auto&& t) {
    use(std::get<4>(t));
});
```

也不代表它可以替代需要编译期值的代码：

```cpp
template <auto Value>
struct compile_time_use;
```

维护者给出的核心反例是：可以把字段访问结果用于 `static_assert` 或非类型模板参数时，结构化绑定路径具有原型 visitor 路径不具备的语言级能力。

因此要区分：

| 问题 | 关注点 |
| :--- | :--- |
| 性能 | 优化后是否有额外机器指令 |
| 语义 | 表达式是否允许出现在常量表达式、模板参数和 `constexpr` 函数中 |

“零运行时开销”不能推出“具有相同的编译期语义”。

## 14. 从原型到 Boost.PFR C++14 引擎

Issue 中的原型直接把用户对象视为 `std::tuple`，这适合作为概念验证，但不适合直接成为可移植库实现。后来的 Boost.PFR C++14 路径将问题拆成几个部件：

```text
字段计数
   ↓
字段类型记录（Classic / Loophole 等机制）
   ↓
内部 sequence_tuple / 存储序列
   ↓
计算字段偏移量
   ↓
offset_based_getter 获取字段指针
   ↓
构造字段引用 tuple
```

其中：

- `sequence_tuple` 负责保存字段类型序列；
- `offset_based_getter` 负责根据布局计算字段位置；
- `Loophole` 引擎使用友元注入等技术记录类型；
- 最终返回的是字段引用组成的 tuple-like 结果，而不是强行把原对象变成标准库 tuple。

这是一种重要的工程化变化：**把“类型推导”和“内存访问”分离**。但 C++14 回退引擎仍然会受到布局、别名规则、`reinterpret_cast` 和 `constexpr` 限制。

## 15. 技术方案的适用条件

使用这类算法前，应至少检查：

1. 类型是否是无基类或满足实现要求的聚合体；
2. 是否可以用聚合初始化完整构造；
3. 字段是否包含会产生副作用的构造/析构逻辑；
4. 是否需要在 `constexpr` 或非类型模板参数上下文使用结果；
5. 当前编译器和标准库是否支持所使用的布局假设；
6. 是否包含匿名字段、C 数组、`const` 字段、引用字段或复杂模板构造函数；
7. 是否能接受 C++14 回退引擎与 C++17 路径在行为和限制上的差异。

适合的场景通常是：

- 配置结构体遍历；
- 简单聚合体序列化；
- 调试打印；
- 运行时字段比较；
- 需要兼容 C++14 的 tuple-like 算法。

不适合直接依赖于：

- 严格可移植的标准对象模型；
- 编译期反射值计算；
- 对构造副作用敏感的类型；
- 需要成员名称的框架；
- 任意复杂类层次结构。

## 16. 最终理解

Issue #5 的核心技术链条可以压缩为：

```text
聚合初始化可检测
→ 用 ubiq 得到字段数量
→ 用 deducer 的转换目标得到字段类型
→ 用递归参数包保存类型列表
→ 用 visitor 复用 tuple 算法
```

它的真正创新点不是 `reinterpret_cast`，而是前面的两个编译期观察：

1. 聚合初始化器的数量可以用 SFINAE 探测；
2. 隐式转换运算符的目标类型可以反向暴露字段类型。

而 `reinterpret_cast` 只是原始原型为了快速获得 tuple 接口所采用的工程捷径，也是后来实现必须重点规避或隔离的风险来源。

一句话总结：**C++14 没有结构化绑定时，仍可以利用聚合初始化和隐式转换完成“字段类型发现”；但字段发现、字段访问的合法性、常量表达式能力和运行时安全性是四个不同问题，不能因为前者成功就认为后者全部成立。**
