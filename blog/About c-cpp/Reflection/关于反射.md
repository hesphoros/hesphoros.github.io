# 反射

反射（Reflection）**是指程序在**运行期（Runtime）能够观察、检验甚至修改自身结构和行为的能力。

简单来说，如果一个语言支持反射，你就可以在程序运行的时候：

- 根据类名字符串（如 `"Person"`）直接创建出该类的对象。
- 遍历一个类的所有成员变量名、函数名和参数类型。
- 根据动态传入的成员名称（如 `"age"` 或 `"sayHello"`）直接读取变量或调用函数。

###  C++ 是否具有原生的反射机制?

C++ 原生目前没有完整强力的反射机制。

- **C++ 的设计哲学**：追求“不为不使用的东西付出一个字节/周期的代价”（零开销抽象，Zero-overhead principle）。编译后的 C++ 代码会被直接翻译成机器码，类名、成员名、类型信息等大多数元数据（Metadata）在编译期就被丢弃（Strip）了，运行时只保留了内存地址和偏移量。
- **现有的伪反射机制**：C++ 仅提供了非常弱的 **RTTI（运行时类型识别）**，比如 `typeid` 和 `dynamic_cast`，但这只能让你知道一个对象的实际类型名称或进行向下类型转换，**无法**动态获取类的成员列表，也**无法**根据名字创建对象。

### 主流框架是如何实现“反射”的？

由于反射在**序列化/反序列化（如 JSON/XML 解析）**、**RPC 框架**、游戏引擎（如 Unreal Engine/Qt）**和**脚本语言绑定（如 Lua/Python）中是刚需，C++ 开发者通常采用以下几种方案：

| **实现方案**                | **原理/实现方式**                                            | **代表应用 / 例子**                                          |
| --------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **代码生成器 / 预编译器**   | 在编译前用外部工具扫描代码，识别特定的标记宏，自动生成包含元数据的额外 C++ 代码。 | **Unreal Engine**（`UPROPERTY()`, `UFUNCTION()`）  **Qt**（MOC，元对象编译器） |
| **宏与模板注册**            | 利用 C++ 的模板元编程（Template Metaprogramming）和宏，手动或半自动地把类及其成员登记到一个全局注册表（Registry）中。 | **RTTR** (Run Time Type Reflection 库)  各种轻量级 JSON 库   |
| **编译期元编程 (C++17/20)** | 利用 `std::tuple`、结构化绑定（Structured Binding）以及 constexpr 技术，在编译期提取并遍历聚合体（Aggregate type）的属性。 | **Magic_Enum** (枚举反射)  PFR (Boost.PFR)                   |

### 实现难点

C++ 的反射实现因其“编译期与运行期的权衡”而独具特色。下面从**核心痛点**、**主流实现机制**到**未来 C++26 静态反射**进行深度拆解。

### 为什么 C++ 实现反射极其困难？

在 C# 或 Java 中，编译器会生成丰富且标准化的元数据（Metadata）并打包进字节码（如 `.dll` 或 `.class`），虚拟机（CLR/JVM）在运行时可以随时读取这些元数据。

而 C++ 面对的是完全不同的底层现实：

- **元数据彻底抹去**：编译完成后，所有的类名、函数名、变量名均被转换为机器码、相对内存偏移量（Offset）或被指针直接替换。
- **内存布局严格紧凑**：C++ 结构体在内存中就是一串连续的字节，没有额外的空间来隐式存入“我是什么类型”、“我有哪些字段”的信息。
- **强类型与无通用运行时**：C++ 缺乏一个像 JVM 那样的统一代理运行时，导致任何动态查找行为都必须依靠额外的数据结构来模拟。

### 一些现代 C++ 工业界的三种主流反射方案

为了在缺乏原生支持的情况下解决序列化、编辑器交互和 RPC 等需求，工业界总结出了三套成熟的解决方案：

#### 方案 A：手动/宏注册模式（以第三方库 RTTR 为例）

通过模板和宏，在程序启动时将类及其成员手动“挂载”到一个全局的元数据注册表中。

```c++
#include <rttr/registration>
using namespace rttr;

struct Monster {
    std::string name;
    int hp;
    void attack() { /* ... */ }
};

// 手动注册元数据
RTTR_REGISTRATION {
    registration::class_<Monster>("Monster")
        .constructor<>()
        .property("name", &Monster::name)
        .property("hp", &Monster::hp)
        .method("attack", &Monster::attack);
}

// 运行期通过字符串反射使用
void test() {
    type t = type::get_by_name("Monster");
    variant var = t.create(); // 动态创建实例
    
    // 动态设置属性
    property prop = t.get_property("hp");
    prop.set_value(var, 100);
}
```

- **优点**：无需外部工具，纯 C++ 代码即可实现，性能可控。
- **缺点**：侵入性强，需要手动书写大量注册代码，维护成本高且容易漏写。

#### 方案 B：预编译器与代码生成（以 Unreal Engine 和 Qt 为例）

通过自定义的预处理工具扫描源码中的“标记宏”，提取元数据并自动生成编译所需的 `.generated.h` 或 `moc_xxx.cpp` 文件。

**Unreal Engine (UHT) 示例：**

```c++
// Unreal Header Tool 会扫描 UCLASS() / UPROPERTY() 宏标记
UCLASS()
class AMyCharacter : public ACharacter {
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Stats")
    float Health;

    UFUNCTION(BlueprintCallable, Category = "Actions")
    void Jump();
};
```

- **工作流**：
  1. `UHT (Unreal Header Tool)` 扫描 `.h` 源文件。
  2. 提取标记了 `UPROPERTY()` 的变量及其类型、分栏等信息。
  3. 自动生成包含类型注册代码的 C++ 源文件并参与最终编译。
- **优点**：开发体验极佳，自动化程度高，支持自动暴露出给蓝图（Blueprint）或编辑器控件使用。
- **缺点**：依赖构建系统的额外编译步骤，增加了编译等待时间。

#### 方案 C：基于现代 C++ 的无侵入编译期萃取（Boost.PFR）

利用 C++17 的**结构化绑定（Structured Binding）**与模板元编程，在**完全不写宏、不改动结构体定义**的前提下萃取字段。

```c++
#include <iostream>
#include <boost/pfr.hpp>

struct Point {
    int x;
    int y;
    double z;
};

int main() {
    Point p{10, 20, 30.5};

    // 编译期获取字段数量
    constexpr auto size = boost::pfr::tuple_size_v<Point>; // = 3

    // 遍历所有字段（无需注册）
    boost::pfr::for_each_field(p, [](const auto& field, std::size_t idx) {
        std::cout << "Field " << idx << ": " << field << "\n";
    });
}
```

- **原理技巧**：借助 C++17 聚合体初始化的特性，通过复杂的模板技巧在编译期探测“结构体可以用几个参数展开”，从而推导出成员个数与类型。
- **局限**：仅支持聚合体类型（Aggregate Types），且**无法获取变量的名字符串**（如能拿到值 `10`，但不知道变量名叫 `"x"`）。

### 未来的标准：C++26 静态反射（Static Reflection）

C++26 引入的静态反射提案（如 P2996）彻底改变了游戏规则。它摒弃了运行时的开销，选择在**编译期**提供强大的元数据查询能力，配合 **`reflexpr` / `^` 运算符** 和 **`constexpr` 注入**。

它的工作机制如下：

#### 1. 使用 `^` 获取反射操作符（Reflect operator）

```c++
struct Player {
    std::string name;
    int level;
};

// 编译期提取 Player 的元数据句柄
constexpr auto meta_player = ^Player; 
```

#### 2. 在编译期遍历与提取信息



```c++
#include <experimental/meta>

template <typename T>
void serialize_to_json(const T& obj) {
    // 编译期获取 T 的所有数据成员列表
    constexpr auto fields = std::meta::members_of(^T);
    
    std::cout << "{\n";
    template for (constexpr auto field : fields) {
        // [: field :] 称为 splice 语法，将反射句柄还原为实际成员引用
        std::cout << "  \"" << std::meta::name_of(field) << "\": "
                  << obj.[:field:] << ",\n";
    }
    std::cout << "}\n";
}
```

#### 静态反射的核心特征总结

| **维度**     | **传统动态反射 (Java/C#)**             | **C++26 静态反射**                                 |
| ------------ | -------------------------------------- | -------------------------------------------------- |
| **触发时机** | 运行时（Runtime）                      | 编译期（Compile-time）                             |
| **性能损耗** | 有（存在内存开销、虚表查找、动态解析） | **零运行时开销**（生成的代码与手动硬编码完全一致） |
| **类型安全** | 较弱（依赖运行时强转，易发生类型抛错） | 极高（类型不匹配在编译时即报错）                   |
| **应用场景** | 插件加载、动态解析未知对象             | 高效序列化、自动化RPC、编译期代码生成              |
