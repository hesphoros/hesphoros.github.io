所有的反射都可以分为以下三个步骤
1. Generate Metadata（Metadata见下文）
2. Query Metadata
3. Operate Metadata

# Generate Metadata

在 C/C++ 中，“Metadata”（元数据）并没有一个统一的官方定义，而是指**描述数据的数据**或**描述代码结构的信息**。它不像在 Java 或 C# 中那样有统一的原生反射框架，而是分散在编译、链接、运行和源码层面的多个维度中。

根据作用阶段和形态，C/C++ 中的 Metadata 可以分为以下五大类：

**1. 编译器和链接器层面的元数据（存在于目标文件/可执行文件中）**
这是操作系统和加载器看到的元数据，用于程序如何被加载、链接和运行。

- **符号表（Symbol Table）**：在编译生成的 `.o`/`.obj` 文件中，记录了全局函数名、全局变量名及其地址。链接器通过它来解析外部引用（外部符号）。
- **调试信息（Debug Info）**：如 DWARF（Linux）或 PDB（Windows）。包含了源代码文件名、行号、变量类型、函数参数等信息。这部分元数据**不会**被加载到最终运行的代码段中，只在调试器（如 GDB、WinDBG）中使用。
- **节区头部（Section Headers）**：如 `.rodata`（只读数据）、`.bss`（未初始化数据）、`.text`（代码段）的起始地址和大小。动态链接器需要这些元数据来重定位地址。

**2. 运行时类型识别（RTTI）—— C++ 特有**
这是 C++ 唯一**原生内置**的运行时元数据机制。

- 当启用 RTTI（`typeid` 和 `dynamic_cast`）时，编译器会为含有虚函数的类生成一个 **虚函数表（vtable）**，并在表头或独立结构中存储 **type_info** 对象。
- 这个 `type_info` 包含类的名称、继承层次关系等元数据。它允许你在运行时通过 `typeid(obj).name()` 获取类型名，或安全地向下转型。

**3. 源码级属性（Attributes）—— C++11 及以后**
这是写给**编译器**看的元数据，用于指导编译行为、优化或静态分析，**不会**生成可执行代码指令。

- 标准语法：`[[noreturn]]`（函数不返回）、`[[deprecated]]`（已弃用）、`[[fallthrough]]`（显式穿透）等。
- 编译器扩展：如 GCC/Clang 的 `__attribute__((packed))`（紧凑结构体）、`__attribute__((aligned))`（内存对齐）、MSVC 的 `__declspec(dllexport)`（导出动态库）。这些属性告诉编译器如何特殊处理变量或函数。

**4. 内存布局元数据（隐式元数据）**
虽然 C/C++ 是静态编译语言，但编译器在背后注入了隐式的内存管理元数据：

- **虚函数表指针（vptr）**：每个含虚函数的对象头部隐含一个指向 vtable 的指针，这是多态调用的元数据索引。
- **堆内存管理（Heap Metadata）**：当你用 `malloc`/`new` 分配内存时，分配器（如 ptmalloc、jemalloc）会在实际返回给你的内存块**前面**附加头部元数据（记录该块的大小、是否空闲、相邻块信息等），用于 `free`/`delete` 时的回收与合并。

**5. 自定义业务元数据（程序员手动构建）**
因为 C/C++ 没有内置的完整反射机制，当需要“运行时知道字段名/属性”时，程序员**必须手动**构造元数据：

- 使用宏定义（`#define`）或枚举生成“字段名 ↔ 偏移量/类型”的映射表。
- 用于**序列化/反序列化**（JSON、XML、Protobuf）、**ORM 框架**或**插件系统**。例如，Qt 的 **MOC（元对象编译器）** 就是通过额外预处理步骤，生成了包含类名、信号/槽信息的巨大元数据结构，从而模拟出 Java 风格的反射。

**举个例子**：如果你定义一个 `struct Person { int age; char* name; };`，编译后，`.text` 中只有 `age` 相对结构体起始地址的偏移量（`0`）和 `name` 的偏移量（`8`）。**程序运行期间，绝对没有** "age" 这个字符串名字与内存地址的对应关系——这就是 C/C++ 元数据“匮乏”的本质。如果你需要这种映射，就必须自己写代码生成一个 `std::map<std::string, size_t>` 来充当元数据表。

目前 C++ 编译器只会保留类型名用于实现 RTTI，即标准中 std::type_info 的相关设施。其他的信息，编译器都会抹除掉。

# Query Metadata

成完之后，接下来就是查询元数据了。很多语言内置的反射模块，例如 Python 的 inspect，Java 的 Reflection，C# 的 System.Reflection，其实就是封装了一些操作，使得用户不用直接接触原始的元数据，用起来更加方便。

值得注意的是，上面这些案例中的查询都是发生在运行时的。在运行时根据字符串进行搜索和匹配，这其实是一个比较慢的过程，所以我们常说反射调用方法比正常调用方法慢。

对于 C++ 来说，编译器提供了一些有限的接口让我们在编译时访问（反射）一些信息，例如使用 decltype 可以获取一个变量的类型，进一步还能判断两个变量类型是否相等，是否是某个类型的子类等等，但是功能十分有限。

不够可以自己生成元信息，把它们都标记为 constexpr，然后就可以在编译期进行查询。事实上 C++26 的静态反射也就是这个思路，由编译器生成元信息，暴露给用户一些接口进行查询。

当然了，编译期可做的事情肯定是没有运行期那么多的，例如希望根据运行时的类型名创建类实例，无论如何编译期肯定没法做到。但你可以基于这些静态的元信息构建动态反射。

# Operate Metadata

然后，就是根据元数据进行进一步的操作，比如代码生成。这个在 C++ 中可以理解为编译期的代码生成，在 Java 和 C# 则可以认为是运行期的代码生成。
