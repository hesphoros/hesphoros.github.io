## 一、 核心概念：什么是 RPC？

**RPC** 是 **Remote Procedure Call**（远程过程调用）的缩写。

在单体应用时代，所有的函数都在同一个进程内。比如你想获取用户信息，直接在代码里调用：

```c
User user = GetUserInfo(userId); // 本地调用：直接从内存栈中跳转到函数地址
```

但随着业务变大，系统被拆分成了**微服务**。`GetUserInfo` 这个函数可能被移到了另一台服务器（服务B）上，而你的业务代码在服务器A上。

这时，你不能像以前那样直接调用了。你必须通过网络，把 `userId` 传给服务B，服务B查到数据后，再通过网络把结果传回服务A。

> **RPC 的核心目标就是：** 让程序员在调用**远程服务器**上的函数时，体验就像调用**本地函数**一样简单、透明，完全感觉不到中间跨越了网络。

## 二、 为什么要 RPC “框架”？（不用框架会怎样）

如果不使用 RPC 框架，单纯用最原始的 HTTP 或 Socket 编程来实现跨服务器调用，服务器A的程序员每次写代码都要清点以下这堆“破事”：

1. **建立网络连接：** 怎么建立 TCP 连接？怎么管理连接池？遇到网络闪断怎么办？
    
2. **序列化（Serialization）：** 内存里的对象/结构体（比如 C++ 的 `struct` 或 Java 的 `Object`）是不能直接在网络上传输的。必须先把它转成二进制字节流（这个过程叫序列化），对方收到后再还原（反序列化）。
    
3. **寻址与路由：** 我怎么知道服务B部署在哪个 IP 和端口上？如果有 10 台服务器都装了服务B，我应该调哪一台（负载均衡）？
    
4. **异常处理：** 如果服务B超时了没回应，我是重试，还是直接报错？
    

如果每个开发人员都要自己去写一遍这套复杂的网络、编解码、容错逻辑，开发效率会极低，且极其容易写出 Bug。

**RPC 框架应运而生。** 它把上述所有与业务无关的、底层的网络通信和数据转换全部封装起来。你只需要定义好接口，剩下的脏活累活全由框架搞定。

## 三、 RPC 框架的经典架构与工作流程

一个标准的 RPC 框架，为了实现“让远程调用像本地调用一样”的效果，内部通常由以下几个核心组件协同工作：

### 1. 核心组件

- **Client Stub (客户端存根 / 代理)：** 这是在客户端生成的“替身”函数。当你在代码里调用 `GetUserInfo` 时，你实际上调用的是这个 Stub。它负责把你的调用请求打包。
    
- **序列化器 (Serializer / Codec)：** 负责将请求参数（如对象、结构体）转成网络可传输的二进制流；以及将收到的二进制响应还原。
    
- **运输层/通信模块 (Transport)：** 负责底层的网络传输（基于 TCP/UDP，或者是 HTTP/2），把二进制流发送到对端。
    
- **Server Stub (服务端存根 / 骨架 Skeleton)：** 服务端的接收器。它收到二进制流后，调用反序列化，然后真正地去调用服务端的本地业务代码。
    

### 2. 经典工作流水线（以一次调用为例）

我们可以把一次 RPC 调用分为 **10 个标准步骤**：

```
[客户端业务代码] ──调用──> [Client Stub]
                                │
                        将方法名和参数序列化
                                │
                                ▼
 [服务端业务代码] <──调用── [Server Stub] ──通过网络发送───-─┐
        │                       ▲                         │
     反序列化                  反序列化                    │
        │                       │                         ▼
        └──返回结果──> [Server Stub] <── 网络返回── [Client Stub]
```

1. **User Client：** 客户端代码像调用本地方法一样，调用 `GetUserInfo(123)`。
    
2. **Client Stub：** 拦截到这个调用，将方法名、参数类型、参数值（`123`）打包成一个标准的独立消息。
    
3. **Serialization：** 客户端 Stub 将消息序列化为密集的二进制字节流。
    
4. **Transport：** 客户端通过网络（Sockets）将字节流发送给远端服务器。
    
5. **Server Receive：** 服务端网络层接收到这串字节流。
    
6. **Server Stub & Deserialization：** 服务端 Stub 收到字节流，将其反序列化，解析出：“哦，对方想调用 `GetUserInfo` 函数，参数是 `123`”。
    
7. **Real Call：** 服务端 Stub 在本地真正执行 `GetUserInfo(123)`，拿到用户数据对象 `User`。
    
8. **Server Return：** 服务端 Stub 将 `User` 对象序列化为二进制流。
    
9. **Transport Back：** 服务端通过网络将字节流发回给客户端。
    
10. **Client Receive & Unpack：** 客户端 Stub 接收到流，反序列化成 `User` 对象，并作为函数返回值塞给最开始的业务代码。**调用完成。**
    

## 四、 评价一个 RPC 框架好坏的 4 个指标

当你去了解不同的 RPC 框架（如 gRPC、brpc、Dubbo、Thrift）时，业界通常会从以下四个技术点去衡量它们：

| **衡量维度**       | **核心关注点**                          | **常见技术方案**                                 |
| -------------- | ---------------------------------- | ------------------------------------------ |
| **1. 序列化效率**   | 关系到**CPU开销**与**网络带宽**。体积越小、速度越快越好。 | Protobuf, Thrift (二进制) 优于 JSON/XML (文本)    |
| **2. 网络I/O模型** | 关系到服务器能抗住多少**并发连接**。               | 高并发下通常采用 **Epoll + 非阻塞 I/O** (NIO)         |
| **3. 传输协议**    | 决定了数据在网络层是如何组装和分帧的。                | gRPC 绑定 HTTP/2；brpc 支持 baidu_std/HTTP 等多协议 |
| **4. 服务治理**    | 大规模微服务下，框架是否自带高级功能。                | 服务发现（Service Discovery）、负载均衡、熔断限流          |

## 总结

**RPC 框架本质上是一个“高级网络通信代理”。** 它通过在客户端和服务端两侧建立“存根（Stub）”，利用高效的序列化技术和网络 I/O，抹平了本地调用与远程调用之间的鸿沟，成为了现代微服务分布式系统赖以生存的交通基础设施。
